Who owns the statusline call

Installing the statusline on a new VM must not drop the tracking

Claude Code runs one statusLine command. That setting is owned by my-setup (modules/claude_config.sh, skill config-ownership), and it points to agent-statusline's script. So the tracking call should not live inside agent-statusline's display code.

Chained by my-setup (proposed)statusLine = agent-tracker tick | bash statusline-command.sh. tick reads Claude Code's JSON from stdin, writes last_seen.json in the background, and passes the same JSON on to the display. agent-statusline holds no tracking code, so a reinstall or a new display can't remove it. Without agent-tracker installed, my-setup writes the display alone.
One line inside agent-statusline's scriptworks, but a rewrite of the display can silently drop it. Installing the statusline on a VM then decides whether tracking happens.
agent-tracker takes over the statusLine settingtwo projects would fight over one key: whoever installs last wins.
New VM, what gets installedDisplayTracking

my-setup + agent-statusline + agent-trackeryesyes: my-setup sees both and chains them
agent-statusline reinstalled lateryesyes: the chain is in my-setup's setting, not in its script

Choices

How the writes are triggered: options

B · hooks + statusline tick (chosen)written when it happens, only then: no lag, no work while idle. A crash sends no end, so boot_ts and last_seen.json cover it.
A · nothing stored: read Claude Code's files~/.claude/sessions is gone after a crash; no history, no last prompt, no Codex.
C · a daemon polling every N salways running, up to N s late, misses short Claude sessions, still needs a hook for the prompt time.
D · one SQLite file written by every hookevery hook of 10+ Claude sessions takes the same lock; a hook must be fast and never fail. Fine later as a read cache.
E · keep it as today13 streams, 4 "alive?" rules; each new need adds a copy (as resurrect did today).
